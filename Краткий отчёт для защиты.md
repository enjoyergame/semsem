**Краткий отчёт по семестровому проекту**  
**Тема:** «Разработка 2.5D шутера на чистом C и Win32 API»  
  
**1. Архитектура приложения**  
В проекте реализована строгая модульная архитектура, полностью исключающая смешивание системного кода и игровой логики. Взаимодействие между модулями происходит исключительно через передачу указателей на структуры состояния (`GameState` и `InputState`).  
* **Модуль логики (Core):** Оперирует абстрактными математическими координатами. Вместо прямого доступа к пикселям экрана, логика использует алгоритм DDA (Digital Differential Analyzer) для симуляции бросания лучей (Raycasting). Результатом работы модуля является заполнение специального буфера `RenderView`, который хранит массив высот стен для каждого вертикального столбца и отсортированный массив видимых 2D-спрайтов.  
* **Модуль интерфейса (UI):** Изолирован от механик игры. Его задача — транслировать нажатия клавиш ОС в структуру `InputState` и визуализировать `RenderView` с помощью функций библиотеки GDI (`StretchBlt`, `TransparentBlt`).  
  
**2. Игровой цикл**  
Игровой цикл реализован в модуле `main.c` и работает по принципу фиксированного шага (Variable Delta Time). Для обеспечения максимальной плавности был отклонен таймер `SetTimer` и функция `Sleep()`. Вместо этого используется аппаратный таймер высокого разрешения `QueryPerformanceCounter`.  
На каждой итерации цикла происходят следующие шаги:  
1. Обработка системной очереди сообщений (`PeekMessage`), чтобы окно не зависало.  
2. Сбор данных о нажатых клавишах.  
3. Передача `delta_time` в модуль `Core` для обновления позиций объектов независимо от частоты кадров (FPS).  
4. Вызов модуля `UI` для отрисовки кадра в теневом буфере (двойная буферизация) и моментального копирования на экран через `BitBlt` во избежание мерцания.  
  
**3. Возникшие трудности и их решения**  
В ходе разработки был решен ряд сложных нетривиальных задач:  
  
* **Проблема производительности GDI в 3D:** Использование стандартных функций `SetPixel` или `Rectangle` для построения 3D-мира приводит к катастрофическому падению FPS.  
* *Решение:* Использование функции `StretchBlt`. Экран отрисовывается вертикальными полосами шириной в 1 пиксель, которые берутся напрямую из HBITMAP-текстуры и растягиваются до нужной высоты математически.  
* **Проблема перекрытия спрайтов (Z-Fighting):** Враги и пули рисовались поверх стен, даже если находились за ними, так как GDI не имеет встроенной поддержки 3D-глубины.  
* *Решение:* Был написан программный одномерный Z-буфер (`float z_buffer[800]`). Во время просчета стен в него записывается дистанция до препятствия. При отрисовке 2D-спрайтов пиксели выводятся на экран только в том случае, если их математическая дистанция меньше, чем значение в Z-буфере.  
* **Проблема реализации Split-Screen (Кооператива):** При отрисовке нижней половины экрана для второго игрока текстуры могли наслаиваться на интерфейс и верхний экран.  
* *Решение:* Использование механизма областей отсечения GDI — `SelectClipRgn`. Перед вызовом рендера для каждого игрока задается строгая прямоугольная зона, за пределы которой функции отрисовки физически не могут вывести пиксели. 
  
**Итог:** Проект полностью соответствует техническому заданию, обходясь исключительно стандартом C11 и Win32 API. Дополнительно реализованы механики, выходящие за рамки базового задания: 2.5D графика, локальный мультиплеер, процедурная генерация ассетов и продвинутый HUD.
